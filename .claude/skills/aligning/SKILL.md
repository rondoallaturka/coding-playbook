# Aligning

The goal is a shared understanding of what the user wants and why, before any plan exists. Plans most often go wrong because one load-bearing assumption was wrong and the user never saw it, either because it was buried in detail or because it was never stated. This skill makes those assumptions visible and gets them confirmed.

## Start light, go deeper only where it's uncertain

Begin with a quick pass: restate the request in a sentence and find what you're least sure about. If nothing important is uncertain, go straight to the confirmation below. Ask questions only where you find real uncertainty, and think hardest about the ones that matter most.

## One question at a time

- Each message asks exactly one question. Before writing it, decide which question would change the plan most if answered, and ask that one.
- After each answer, stop and think: what did this change, what is now most uncertain, and is it worth another question?
- Reflect back what you heard in a sentence or two before the next question, so the user can catch a misreading early.
- Make questions easy to answer: concrete, in plain language, with multiple-choice options when the likely answers are predictable.

## Socratic, from first principles

- Start from the underlying goal: what problem the user is solving and why it matters to them, before features or methods.
- Help the user think, not just answer. When a request rests on an assumption, ask the question that makes them examine it. They may not have worked out their own principles for this yet; helping them do that is part of the job.
- Test their thinking where it matters, but don't argue past one round. Their answer decides.

## What counts as load-bearing

An assumption deserves the user's attention when:

- much of the work depends on it, so being wrong would waste or undo a lot; or
- it reflects a belief about what matters (a first principle) that the user hasn't confirmed.

Technical choices the user doesn't care about are yours to make.

## Stop at 80/20

Don't get stuck in a question loop. Once the answers that drive most of the value are settled, stop asking and confirm:

> Here's what I understand:
> - **Goal:** [why this matters, in one line]
> - [3 to 6 load-bearing assumptions, in plain language]
> - ⚠️ **Least certain:** [the one or two you're least sure of]
>
> Is this right? Yes, or tell me what's off.

If the user says yes, move on to the plan or the work. If not, ask the one question that best resolves what's off, then confirm again.

## Scale to the task

For a quick, low-stakes request, the whole process can be one line: say what you'll do and your least certain assumption, then do it. Use the full process when a wrong assumption would be costly.
